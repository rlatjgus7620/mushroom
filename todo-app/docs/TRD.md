## 1. 목적

PRD의 MVP 기능(F-01 ~ F-05)을 어떤 기술로, 어떤 구조로 만들지 정한다.

## 2. 기술 스택과 선택 이유

| 기술 | 쓰는 곳 | 왜 골랐나 (한 줄 설명) |
|------|------|------|
| Next.js 15 (App Router) | 화면 + API 서버 | 화면과 서버 API를 한 프로젝트 안에서 같이 만들 수 있어서, 서버를 따로 띄울 필요가 없다. |
| React 19 | 화면 | 화면을 작은 부품(컴포넌트)으로 나눠 만들고, 데이터가 바뀌면 화면이 자동으로 다시 그려진다. |
| TypeScript (strict) | 전체 코드 | 변수에 타입을 붙여서 오타나 잘못된 값을 실행 전에 미리 잡아준다. |
| Tailwind CSS | 스타일 | 별도 CSS 파일 없이 HTML에 클래스 이름만 붙여서 바로 꾸밀 수 있다. |
| MySQL 8 | 데이터 저장 | 가장 널리 쓰이는 무료 관계형 DB 중 하나라서 자료와 예제가 많고, 데이터를 표 형태로 안전하게 저장한다. |
| Drizzle ORM | 서버 ↔ DB 연결 | SQL을 TypeScript 코드로 쓰게 해줘서, DB 테이블 구조와 코드의 타입이 어긋나지 않는다. |
| Zod | 입력값 검증 | "제목은 1~100자" 같은 규칙을 한 번 적어두면 화면과 서버에서 똑같이 검사할 수 있다. |
| Jest + React Testing Library | 테스트 | 사용자가 실제로 클릭하고 입력하는 방식 그대로 화면을 테스트할 수 있다. |

## 3. 전체 구조

```
[브라우저]                      [Next.js 서버]                    [DB]
화면 컴포넌트  ── HTTP 요청 ──▶  API 라우트  ──▶  서버 로직  ──▶  MySQL
(src/components)  ◀── JSON 응답 ──  (app/api)        (src/lib)   ◀──
```

| 폴더 | 역할 |
|------|------|
| app/ | 페이지와 API 라우트 |
| src/components/ | 화면 컴포넌트 (입력창, 목록, 항목 등) |
| src/lib/ | 서버 로직, DB 연결, 검증 규칙 |
| src/types/ | 화면과 서버가 같이 쓰는 타입 |
| docs/ | 명세 문서 |

## 4. 데이터 흐름: "추가" 버튼을 누른 뒤 DB에 저장되기까지 (F-01)

> v0.3(DB 저장) 기준이다. API 규칙은 7장을 따르고, 세부 내용은 API_SPEC.md에서 정한다.

1. **입력**: 사용자가 입력창에 제목을 적고 "추가" 버튼을 누른다.
2. **화면에서 검증**: 화면 컴포넌트가 Zod 규칙으로 제목의 앞뒤 공백을 잘라낸 뒤 검사한다. 비어 있거나 100자를 넘으면 요청을 보내지 않고 안내 메시지를 보여준다.
3. **요청 보내기**: 검사를 통과하면 `fetch`로 서버에 `POST /api/todos` 요청을 보낸다. 제목은 JSON으로 담는다. (예: `{ "title": "우유 사기" }`)
4. **API 라우트가 받기**: `app/api/todos/route.ts`가 요청을 받아 JSON 본문을 꺼낸다.
5. **서버에서 다시 검증**: 같은 Zod 규칙으로 한 번 더 검사한다. 화면 검사는 우회할 수 있으므로 서버 검사가 최종 관문이다. 실패하면 `400` 상태 코드와 오류 응답(7장 형식)을 돌려준다.
6. **서버 로직 호출**: API 라우트가 `src/lib/`의 할 일 생성 함수를 부른다.
7. **DB에 저장**: 생성 함수가 `crypto.randomUUID()`로 id를 만들고, Drizzle로 `todos` 테이블에 새 행을 넣는다. 완료 여부는 `false`, 생성 시각은 지금 시각으로 저장된다.
8. **저장 결과 받기**: MySQL은 저장한 행을 바로 돌려주지 않는다(`RETURNING` 미지원). 그래서 방금 만든 id로 행을 다시 조회해 생성 시각까지 포함한 할 일을 얻는다.
9. **응답 보내기**: API 라우트가 저장된 할 일을 JSON으로 담아 `201` 상태 코드로 응답한다.
10. **화면 갱신**: 화면 컴포넌트가 응답을 받아 목록 상태에 새 할 일을 맨 위에 추가한다. React가 목록을 다시 그린다. (F-02 최신순)

오류가 나면(네트워크 끊김, 서버 오류 등) 목록은 바꾸지 않고 오류 메시지를 보여준다.

> 완료 전환(F-03), 삭제(F-04)도 같은 흐름을 따른다. 요청 방식만 다르다.

## 5. 버전별 저장 위치 (F-05)

| 버전 | 데이터가 저장되는 곳 | 새로고침 후 | 서버 재시작 후 |
|------|------|------|------|
| v0.1 | 브라우저 메모리 (React 상태) | 사라짐 | 사라짐 |
| v0.2 | 서버 메모리 (API 라우트의 배열 변수) | 유지 | 사라짐 |
| v0.3 | MySQL DB | 유지 | 유지 |

- v0.1은 위 흐름의 1~2, 10단계만 있다. 서버 요청 없이 화면에서 바로 목록에 넣는다.
- v0.2는 7~8단계에서 DB 대신 서버 메모리의 배열에 넣는다.
- v0.3에서 7~8단계를 Drizzle + MySQL로 바꾼다. 화면 코드는 바뀌지 않는다.

## 6. 공통 규칙

- **검증**: 제목 규칙(앞뒤 공백 제거 후 1~100자)은 Zod 스키마 하나로 정의하고 화면과 서버가 같이 쓴다.
- **타입**: `any` 타입은 쓰지 않는다. 할 일 타입은 `src/types/`에 두고 화면과 서버가 공유한다.
- **비밀 값**: DB 접속 주소는 `.env` 파일의 환경 변수로 관리하고 git에 올리지 않는다.
- **테스트**: 기능마다 테스트를 작성하고, 테스트를 삭제하거나 skip하지 않는다.

## 7. API 규칙

v0.2부터 적용한다. (v0.1은 API 없이 화면에서만 동작한다.)

### 7.1 엔드포인트

| 기능 | 메서드와 경로 | 요청 본문 | 성공 응답 |
|------|------|------|------|
| 목록 조회 (F-02) | `GET /api/todos` | 없음 | `200` + `Todo[]` (최신순) |
| 추가 (F-01) | `POST /api/todos` | `{ "title": "..." }` | `201` + `Todo` |
| 완료 전환 (F-03) | `PATCH /api/todos/:id` | `{ "completed": true }` | `200` + 바뀐 `Todo` |
| 삭제 (F-04) | `DELETE /api/todos/:id` | 없음 | `204` (본문 없음) |

- **목록 불러오기**: 화면이 열리면 `GET /api/todos`를 `fetch`로 불러온다. 서버 컴포넌트에서 DB를 직접 조회하지 않는다. 모든 기능이 "화면 → API → 서버 로직" 같은 흐름을 따르게 하기 위해서다.
- **완료 전환은 바꿀 값을 직접 보낸다**: 서버가 현재 값을 뒤집는 방식이 아니라, 원하는 값(`true`/`false`)을 보낸다. 같은 요청을 두 번 보내도 결과가 같아서 실수가 적다.
- **페이지 나누기(pagination)는 하지 않는다**: 혼자 쓰는 앱이라 할 일 수가 많지 않다.

### 7.2 응답 형식

- **성공**: 데이터를 감싸지 않고 그대로 돌려준다. (예: `Todo`, `Todo[]`)
- **오류**: 모든 API가 아래 모양으로 돌려준다. (타입은 DATA_MODEL.md의 `ApiErrorResponse`)

```json
{ "error": { "code": "VALIDATION_ERROR", "message": "제목은 1~100자로 입력해주세요." } }
```

### 7.3 상태 코드

| 코드 | 언제 | 오류 code |
|------|------|------|
| `200` | 조회, 완료 전환 성공 | - |
| `201` | 추가 성공 | - |
| `204` | 삭제 성공 | - |
| `400` | 입력값이 규칙에 맞지 않음 | `VALIDATION_ERROR` |
| `404` | 해당 id의 할 일이 없음 | `NOT_FOUND` |
| `500` | 서버 내부 오류 | `INTERNAL_ERROR` |
