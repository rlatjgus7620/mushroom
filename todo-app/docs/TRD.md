## 1. 목적

PRD의 MVP 기능(F-01 ~ F-05)을 어떤 기술로, 어떤 구조로 만들지 정한다.

## 2. 기술 스택과 선택 이유

### 2.1 화면 (프론트엔드)

| 기술 | 쓰는 곳 | 왜 골랐나 (한 줄 설명) |
|------|------|------|
| Next.js 15 (App Router) | 화면 | React 화면을 페이지 단위로 쉽게 만들고, 개발 중 `/api` 요청을 백엔드로 넘겨줄 수 있다. |
| React 19 | 화면 | 화면을 작은 부품(컴포넌트)으로 나눠 만들고, 데이터가 바뀌면 화면이 자동으로 다시 그려진다. |
| TypeScript (strict) | 화면 코드 | 변수에 타입을 붙여서 오타나 잘못된 값을 실행 전에 미리 잡아준다. |
| Tailwind CSS | 스타일 | 별도 CSS 파일 없이 HTML에 클래스 이름만 붙여서 바로 꾸밀 수 있다. |
| Zod | 화면 입력 검증 | "제목은 1~100자" 규칙을 화면에서 먼저 검사해 잘못된 요청을 보내지 않게 한다. |
| Jest + React Testing Library | 화면 테스트 | 사용자가 실제로 클릭하고 입력하는 방식 그대로 화면을 테스트할 수 있다. |

### 2.2 서버 (백엔드)

| 기술 | 쓰는 곳 | 왜 골랐나 (한 줄 설명) |
|------|------|------|
| Python 3.12 | 서버 코드 | 문법이 간단해서 초보자가 읽고 쓰기 쉽다. |
| FastAPI | API 서버 | 짧은 코드로 API를 만들 수 있고, 요청 검증과 API 문서 페이지(`/docs`)를 자동으로 만들어 준다. |
| Uvicorn | FastAPI 실행 | FastAPI 앱을 실제로 띄워 요청을 받게 해주는 서버 프로그램이다. |
| Pydantic v2 | 서버 입력 검증 | 요청 데이터의 모양과 규칙을 클래스로 적으면 자동으로 검사해준다. FastAPI에 기본으로 들어 있다. |
| PostgreSQL 16 | 데이터 저장 | 무료이면서 가장 많이 쓰이는 관계형 DB 중 하나로, 기능이 풍부하고 안정적이다. |
| SQLAlchemy 2.0 | 서버 ↔ DB 연결 | SQL을 파이썬 코드로 쓰게 해주는 가장 널리 쓰이는 ORM이다. |
| Alembic | DB 구조 변경 기록 | 테이블을 만들거나 바꾼 내역을 파일로 남겨, 어느 컴퓨터에서든 같은 DB 구조를 만들 수 있다. |
| psycopg 3 | DB 드라이버 | 파이썬이 PostgreSQL과 실제로 통신하게 해주는 연결 도구다. |
| pytest + TestClient | API 테스트 | 서버를 띄우지 않고도 API에 요청을 보내 응답을 확인할 수 있다. |

## 3. 전체 구조

```
[브라우저]           [Next.js 개발 서버 :3000]          [FastAPI :8000]              [DB]
화면 컴포넌트 ──요청──▶ /api/* 를 그대로 전달 ──▶ API 라우터 ─▶ 서버 로직 ─▶ PostgreSQL
              ◀─JSON──                     ◀──                                ◀──
```

- 화면은 Next.js, API와 DB 처리는 FastAPI가 맡는다. 개발 중에는 서버 두 개(3000번, 8000번 포트)를 함께 띄운다.
- **요청 전달(프록시)**: 화면은 항상 같은 주소의 `/api/todos`로 요청한다. Next.js 설정(`rewrites`)이 이 요청을 FastAPI(`http://localhost:8000/api/todos`)로 넘긴다.
  - 브라우저 입장에서는 같은 주소로만 요청하므로 CORS(다른 주소 요청 허용) 설정이 필요 없다.
  - 화면 코드의 요청 경로가 백엔드 주소와 상관없이 그대로 유지된다.

### 3.1 폴더 구조

| 폴더 | 역할 |
|------|------|
| app/ | 페이지 (API 라우트는 두지 않는다) |
| src/components/ | 화면 컴포넌트 (입력창, 목록, 항목 등) |
| src/lib/ | 화면용 함수 (API 호출, Zod 검증 규칙) |
| src/types/ | 화면에서 쓰는 타입 |
| \_\_tests\_\_/components/ | 화면 테스트 (Jest) |
| backend/app/ | FastAPI 앱 (라우터, Pydantic 스키마, DB 모델, DB 연결) |
| backend/tests/ | API 테스트 (pytest) |
| backend/alembic/ | DB 구조 변경 기록 (v0.3부터) |
| docs/ | 명세 문서 |

## 4. 데이터 흐름: "추가" 버튼을 누른 뒤 DB에 저장되기까지 (F-01)

> v0.3(DB 저장) 기준이다. API 규칙은 7장을 따르고, 세부 내용은 API_SPEC.md에서 정한다.

1. **입력**: 사용자가 입력창에 제목을 적고 "추가" 버튼을 누른다.
2. **화면에서 검증**: 화면 컴포넌트가 Zod 규칙으로 제목의 앞뒤 공백을 잘라낸 뒤 검사한다. 비어 있거나 100자를 넘으면 요청을 보내지 않고 안내 메시지를 보여준다.
3. **요청 보내기**: 검사를 통과하면 `fetch`로 `POST /api/todos` 요청을 보낸다. 제목은 JSON으로 담는다. (예: `{ "title": "우유 사기" }`)
4. **요청 전달**: Next.js 개발 서버가 요청을 FastAPI(`localhost:8000`)로 그대로 넘긴다.
5. **API 라우터가 받기**: FastAPI의 할 일 라우터가 요청을 받는다.
6. **서버에서 다시 검증**: Pydantic 스키마로 한 번 더 검사한다(앞뒤 공백 제거 후 1~100자). 화면 검사는 우회할 수 있으므로 서버 검사가 최종 관문이다. 실패하면 `400` 상태 코드와 오류 응답(7장 형식)을 돌려준다.
7. **DB에 저장**: 서버 로직이 SQLAlchemy로 `todos` 테이블에 새 행을 넣는다. `id`, 완료 여부(`false`), 생성 시각은 DB 기본값으로 정해진다.
8. **저장 결과 받기**: PostgreSQL은 `INSERT ... RETURNING`으로 저장된 행(id, 생성 시각 포함)을 바로 돌려준다.
9. **응답 보내기**: FastAPI가 저장된 할 일을 JSON으로 바꿔(`created_at` → `createdAt`) `201` 상태 코드로 응답한다. Next.js가 이 응답을 다시 브라우저로 전달한다.
10. **화면 갱신**: 화면 컴포넌트가 응답을 받아 목록 상태에 새 할 일을 맨 위에 추가한다. React가 목록을 다시 그린다. (F-02 최신순)

오류가 나면(네트워크 끊김, 서버 오류 등) 목록은 바꾸지 않고 오류 메시지를 보여준다.

> 완료 전환(F-03), 삭제(F-04)도 같은 흐름을 따른다. 요청 방식만 다르다.

## 5. 버전별 저장 위치 (F-05)

| 버전 | 데이터가 저장되는 곳 | 새로고침 후 | 서버 재시작 후 |
|------|------|------|------|
| v0.1 | 브라우저 메모리 (React 상태) | 사라짐 | 사라짐 |
| v0.2 | FastAPI 서버 메모리 (파이썬 리스트) | 유지 | 사라짐 |
| v0.3 | PostgreSQL DB | 유지 | 유지 |

- v0.1은 위 흐름의 1~2, 10단계만 있다. 서버 요청 없이 화면에서 바로 목록에 넣는다.
- v0.2는 7~8단계에서 DB 대신 FastAPI 서버 메모리의 리스트에 넣는다. `id`(`uuid4`)와 생성 시각은 서버 코드가 만든다.
- v0.3에서 7~8단계를 SQLAlchemy + PostgreSQL로 바꾼다. 화면 코드와 API 모양은 바뀌지 않는다.

## 6. 공통 규칙

- **검증**: 제목 규칙(앞뒤 공백 제거 후 1~100자)을 화면은 Zod로, 서버는 Pydantic으로 각각 적는다. 언어가 달라 규칙을 한 파일로 공유할 수 없으므로, 두 규칙이 같은지 TEST_CASES.md의 같은 경계값으로 확인한다.
- **타입**: 화면은 `any` 타입을 쓰지 않고, 서버 파이썬 코드에는 타입 힌트를 붙인다. 화면 타입(`src/types/`)과 서버 스키마(Pydantic)의 필드 이름은 API_SPEC.md에 맞춘다.
- **이름 규칙**: 파이썬과 DB는 `snake_case`(`created_at`), API JSON과 화면은 `camelCase`(`createdAt`)를 쓴다. 바꾸는 일은 Pydantic이 맡는다.
- **비밀 값**: DB 접속 주소(`DATABASE_URL`)는 `backend/.env` 파일의 환경 변수로 관리하고 git에 올리지 않는다.
- **테스트**: 기능마다 테스트를 작성하고, 테스트를 삭제하거나 skip하지 않는다.

## 7. API 규칙

v0.2부터 적용한다. (v0.1은 API 없이 화면에서만 동작한다.)

### 7.1 엔드포인트

| 기능 | 메서드와 경로 | 요청 본문 | 성공 응답 |
|------|------|------|------|
| 목록 조회 (F-02) | `GET /api/todos` | 없음 | `200` + `Todo[]` (최신순) |
| 추가 (F-01) | `POST /api/todos` | `{ "title": "..." }` | `201` + `Todo` |
| 완료 전환 (F-03) | `PATCH /api/todos/{id}` | `{ "completed": true }` | `200` + 바뀐 `Todo` |
| 삭제 (F-04) | `DELETE /api/todos/{id}` | 없음 | `204` (본문 없음) |

- **목록 불러오기**: 화면이 열리면 `GET /api/todos`를 `fetch`로 불러온다. 모든 기능이 "화면 → API → 서버 로직" 같은 흐름을 따르게 하기 위해서다.
- **완료 전환은 바꿀 값을 직접 보낸다**: 서버가 현재 값을 뒤집는 방식이 아니라, 원하는 값(`true`/`false`)을 보낸다. 같은 요청을 두 번 보내도 결과가 같아서 실수가 적다.
- **페이지 나누기(pagination)는 하지 않는다**: 혼자 쓰는 앱이라 할 일 수가 많지 않다.

### 7.2 응답 형식

- **성공**: 데이터를 감싸지 않고 그대로 돌려준다. (예: `Todo`, `Todo[]`)
- **오류**: 모든 API가 아래 모양으로 돌려준다. (타입은 DATA_MODEL.md의 `ApiErrorResponse`)

```json
{ "error": { "code": "VALIDATION_ERROR", "message": "제목은 1~100자로 입력해주세요." } }
```

### 7.3 상태 코드

| 코드 | 언제 | 오류 code |
|------|------|------|
| `200` | 조회, 완료 전환 성공 | - |
| `201` | 추가 성공 | - |
| `204` | 삭제 성공 | - |
| `400` | 입력값이 규칙에 맞지 않음 | `VALIDATION_ERROR` |
| `404` | 해당 id의 할 일이 없음 | `NOT_FOUND` |
| `500` | 서버 내부 오류 | `INTERNAL_ERROR` |

### 7.4 FastAPI 기본 동작과 다른 점

FastAPI의 기본 동작을 그대로 쓰면 위 규칙과 달라지는 부분이 있어, 서버에서 맞춰준다.

- **검증 실패는 `400`으로 바꾼다**: FastAPI는 기본으로 `422`와 자체 오류 모양을 돌려준다. 오류 처리기(exception handler)에서 `400`과 7.2 형식으로 바꾼다. (JSON 형식 오류 포함)
- **id는 문자열로 받는다**: 경로의 `{id}`를 `UUID` 타입으로 받으면 형식이 틀린 id에 FastAPI가 `422`를 돌려준다. 문자열로 받아서, 형식이 틀리거나 없는 id는 모두 `404`로 처리한다.
- **예상하지 못한 오류는 `500`으로 감싼다**: 오류 내용(DB 오류 메시지 등)은 응답에 담지 않는다.

## 8. 열린 질문

- 배포는 어디로 할 것인가? 화면(Next.js)은 Vercel이 유력하고, FastAPI 서버와 PostgreSQL을 올릴 곳은 따로 정해야 한다. 배포하면 프록시 대상 주소도 바뀐다.
- PostgreSQL은 개발할 때 어떻게 띄울 것인가? (로컬 설치 또는 Docker)
